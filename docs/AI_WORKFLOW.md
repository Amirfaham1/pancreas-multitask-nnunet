## Workflow used

### 1. Requirement extraction before implementation

Codex reads the supplied assessment, translates each requirement into an implementation or artifact contract, and records uncertainty rather than silently choosing an interpretation. Amirfaham confirms the delivery priority: the strongest defensible undergraduate submission, with higher-tier engineering work attempted only after required artifacts are safe.

Examples of requirement-to-evidence mapping:

| Requirement | Planned evidence |
|---|---|
| nnU-Net v2 3D ResEnc M | Network construction/configuration plus architecture contract test |
| Shared encoder, two task outputs | Gradient and tensor-shape tests; diagram in report |
| W&B tracking for both tasks | Public or reviewer-accessible run URL and exported run summary |
| Class imbalance and overfitting strategy | Configuration, rationale, and learning curves |
| Validation metrics | Case-level and aggregate metric artifacts |
| No validation training | Immutable split manifest and data-loader tests |
| No external data/pre-trained weights | Dataset and checkpoint provenance statement |
| AI workflow | This document and condensed report section |
| Test masks and subtype CSV | Automated archive contract validation |

### 2. Data audit with immutable source files

AI-assisted scripts inspect case counts, pairings, NIfTI metadata, value ranges, and label sets. A source audit identified that many masks decode the intended pancreas label as a near-integer float rather than exact integer `1`. The correction is deterministic conversion into a separate nnU-Net dataset; the supplied files remain unchanged.

Every automated correction must answer:

- Which files were affected?
- Which exact source values were mapped?
- Was shape/affine/spacing preserved?
- Does the converted set contain only allowed labels?
- Can the conversion be repeated from a manifest and command?

### 3. Small tests before expensive runs

Codex first generates tests for high-risk contracts: output shapes, shared-encoder gradients, classification label mapping, fixed split membership, finite losses, prediction naming, and archive structure. A one-batch forward/backward smoke test is required before any long training run.

This ordering matters because GPU time is scarce and a model that trains is not necessarily a model that satisfies the assessment contract.

### 4. Evidence-backed experimentation

Each run is tied to:

- a Git commit;
- an explicit configuration;
- a dataset fingerprint/split manifest;
- the deliberately nondeterministic training policy and deterministic evaluation seed;
- hardware and environment versions;
- a W&B run ID;
- saved checkpoints and metric artifacts.

Codex may recommend changes based on loss curves or failures, but no result is reported until the saved checkpoint is re-evaluated. Failed and superseded experiments stay in `WORKLOG.md`.

### 5. Human review at consequential boundaries

Amirfaham is asked to participate where AI cannot or should not act alone:

- authenticating to W&B, GitHub, or hosted GPU services without exposing secrets;
- approving public release;
- choosing between deadline-driven trade-offs when evidence is incomplete;
- reviewing whether the report reflects the implementation and his intended submission;
- opening the final files and submitting them.

### 6. Artifact-derived reporting

Tables are populated from exported metrics wherever possible. Manual transcription is cross-checked. Unmeasured fields remain visibly marked as unfinished during development; neither plausible values nor W&B dashboard impressions are substituted for evaluation output.

### 7. Final adversarial check

Before delivery, the workflow attempts to disprove that the submission is ready:

- extract the ZIP into a clean temporary directory;
- verify exact case counts and names;
- read every NIfTI and validate geometry/dtype/labels;
- validate every CSV row and prediction class;
- compare report numbers against metric artifacts and W&B;
- scan Git history/worktree for datasets, tokens, private paths, and oversized files;
- follow the README from a clean environment as far as time and compute permit.

## Validation of AI-generated work

AI output is treated as an untrusted draft until checked. Verification is proportional to consequence:

| Risk | Validation |
|---|---|
| Incorrect label conversion | Before/after unique-value audit, geometry equality, spot checks |
| Data leakage | Split-manifest assertions and case-ID intersection check |
| Wrong architecture | Class/config inspection, output-shape test, gradient-flow test |
| Silent loss bug | Unit tests on synthetic inputs and finite-gradient smoke test |
| Misleading metric | Synthetic metric tests, explicit definitions, case-level exports |
| W&B mismatch | Compare exported summary with local evaluation artifacts |
| Invalid predictions | Full test-output contract validator |
| Fabricated report statement | Claim-to-artifact review and retained placeholders |
| Privacy or credential leak | Git/worktree scan before publication |

## Known limitations of the AI workflow

- AI can generate syntactically correct but semantically wrong training code; passing tests reduce but do not eliminate that risk.
- Rapid iteration on one validation split can itself become a form of validation overfitting. The number and nature of model-selection decisions must be disclosed.
- AI cannot guarantee that a short run reaches the requested thresholds, especially for small-lesion segmentation.
- AI cannot provide clinical validation or claim that performance transfers beyond the supplied cropped dataset.
- An exact “percentage of code written by AI” is not intrinsically well-defined after formatting, generated configuration, human edits, and dependency use. The final report will give a transparent estimate and the basis used, not false precision.
- Human review under a deadline may miss subtle issues; automated checks and artifact-based reporting are used to reduce this risk.

## Data, privacy, and security

- Only the supplied de-identified data are used.
- Data, model artifacts containing embedded paths, API tokens, and local environment files are excluded from Git.
- Secrets are entered through normal authentication flows or environment variables and are never pasted into source files or documentation.
- Public release occurs only after Amirfaham’s approval and a repository scan.
- No output is represented as suitable for clinical use.
